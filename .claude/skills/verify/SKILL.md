# Verifying DitoDitoInfinito at runtime

## Launch

- Dev server with rebuild-on-change: `trunk serve --port 8099` (run in the background). It auto-reloads the page on every rebuild, so **do not** use it for long runs while editing.
- Stable static build for long tests: `trunk build --release --public-url / --dist dist-test` then `node .claude/skills/verify/serve.mjs dist-test 8098` (in the background). Not `python3 -m http.server`: it resets connections under the page's parallel requests, and the page then says the browser cannot run the game, now and then.
- `just check` covers native crates, the wasm app, SEO regen and REUSE lint. `just test` runs native tests (chart, engine, xtask).

## Routes (hash router, works under any public URL)

- `#/` silent Start menu; `#/select` song select (step 6.2: the theme's screen on the canvas; fetches `songs/index.json`, generated by `cargo run -p xtask -- gen-songs` as a Trunk pre-build hook). `#/?gfx=gl` (and `auto`, `bias`, `slow`) are carried to the play route that Start opens.
- `#/play?song=<id>&chart=<n>` gameplay; `&auto=1` plays the chart automatically (scripted presses at each note's judged time), `&gfx=gl` forces the WebGL2 backend. Song ids are the directory names under `assets/songs/`. The chart index is the position in `Song::charts` (see the manifest's `charts[].index`).
- `#/calibrate/run?mode=visual|audio|combined` converging calibration on the gameplay path; `&auto=1&bias=<ms>` autoplays with a deliberate late (+) or early (−) bias so convergence can be checked (expect the result card to show `+<bias> ms` and "Converged"). `&bias` also works on `#/play`.
- `#/options` (the theme's screen, "## Options"), `#/calibrate` and `#/credits` (the theme's pages, "## Calibration's menu and the credits"; the credits read `credits/credits.json` from `xtask gen-credits`).
- `#/play?replay=<play id>` a kept play's replay, `&view=results` its results ("### SVG images (both shells draw them alike)

Skins' SVG images are drawn by the SVG worker (`crates/svg-worker`, `web::svg`), with the code desktop uses (`docs/plans/noteskin-svg.md`). `window.__DDI_SVG` is `{drawn, drawingMs}` (images the workers drew, their summed drawing time); `window.__DDI_SVG_LOADS` lists each skin load's `{images, byBrowser, ms}` (its SVGs, how many the browser drew instead, the load's decode time). `window.__DDI_SVG_PIXELS(text, width, height)` resolves to the RGBA rows a worker draws, to compare with desktop's (`ddi_noteskin::raster`; identical bytes in Chrome, Firefox and WebKit, hashed with `crypto.subtle`); `window.__DDI_SVG_BROWSER = true` in an init script draws skins' SVGs with the browser as before, to compare the two. `window.__DDI_SKIN_IMAGES` is the last skin load's image report (`ddi_noteskin::report`: `{skin, summary, hash, pixels, budget, images: [{skin, path, hash, svg, own, decoded, outcome: {kind: kept|by_browser|left_out|failed, why}}]}`; desktop prints the same summary line per skin, with the same images hash for the same files). ## Engine debug state

While a session runs, `window.__DDI_DEBUG` is refreshed every 20 frames (`music_seconds`, the decoded music's length (a `.ssc` chart's own `#MUSIC` when it has one), and `lyrics`, the lyric lines drawn, `.lrc` ones included, and `cover`, the lane covers as the mods line says them (`"hidden+ 17% sudden+ 33%"`, null when off; Page Up/Page Down move them, Enter hides them), are there too): `{frames, backend, srgb_view, song_time, combo, max_combo, taps:[W1..Miss], held, let_go, finished, failed, drift, output_latency, audio, pressed:[per lane], pads, pad_polls, pad_fast}` (`held` counts held notes; `pressed` is which lanes are down right now; `srgb_view` is whether the scene is drawn through an sRGB view, expected `true` on both backends; `text_shaped` counts the HUD runs shaped so far, a few a second in play). `audio` (also a line in the debug overlay) reads e.g. `audio: Running · 48000 Hz · master 1.00 · output peak -20.1 dBFS · volume 0.33`: the output peak comes from an analyser on the master output, so it tells "the game outputs nothing" from "the output goes nowhere". Read it with `page.evaluate(() => window.__DDI_DEBUG)`.

`window.__DDI_FORCE_WASM_DECODE = true` (set before starting a session, e.g. with `page.addInitScript`) skips `decodeAudioData` and decodes the song with the built-in decoder (`ddi_platform::decode`: Ogg Vorbis, Ogg Opus through `rusty-opus`, MP3), the fallback for browsers that cannot decode a file (Safari with Ogg Vorbis, WebKit builds without Opus); the console says "decoded in wasm instead". It is resampled to the context's rate in wasm (Opus is 48 kHz; contexts here are often 44.1 kHz). To compare it with the browser's own decode, wrap `BaseAudioContext.prototype.createBuffer` in an init script to keep the buffer it makes and decode the same file with `decodeAudioData` in the page. Playwright's WebKit decodes Ogg Opus itself, so there too the fallback runs only when forced. The same fallback runs when the browser's decode comes back silent (Safari with Ogg Vorbis); it logs "decodeAudioData returned silence; decoded in wasm instead". Previews play through Web Audio: test them with `--autoplay-policy=document-user-activation-required` so only a real click can start them.

## Imported songs

Song select's "+ Add songs" (footer link `Link.Add`, compact `AddIcon`) opens the import dialog: its buttons (`PickFolder`, `PickFiles`; `NewSong`, "New song from a music file", the page's third input, which takes one music file and opens the chart editor on a new song of the pack `Dito Edits` stored at once, `target/scratch/pw/new-song-web.mjs`) click the page's real, hidden inputs in `.import-panel` inside the gesture, its toggles (`Option.copy`, `Option.videos`, `Option.details`) set the import options, and it shows the status and the report (Noteskins, Not imported, Imported with problems, details) in a scrolled list; `.import-status` (visually hidden, `aria-live`) holds the status line too. The page has two pickers. Where `showDirectoryPicker` exists (Chrome, headless too) "choose folder" is a button that keeps the folder's handle for re-reading; elsewhere it is a hidden `webkitdirectory` input. For the input in Chrome, `page.addInitScript(() => { delete window.showDirectoryPicker; })`: then `.import-panel input[type=file]` index 0 is the folder picker and index 1 takes zips or loose files (without it, only the zip/files input is there). To test the handle path, make the picker return an OPFS folder the test filled (`window.showDirectoryPicker = async () => (await navigator.storage.getDirectory()).getDirectoryHandle('Packs')`; OPFS handles are granted and can be kept in IndexedDB): an open pack imported from it then offers "re-read folder", which imports the folder again and removes the songs from that folder whose folders are gone. Such imports are linked (records carry `links`; the `files` store holds only charts and banners) unless "store a chosen folder's songs in the browser" is ticked. OPFS handles are always granted; to see the start prompt's `access` step ("Allow reading the folder", the `Allow` button, focused: Enter presses it), override `FileSystemHandle.prototype.queryPermission` to answer `prompt` until `requestPermission` (overridden to grant only while `navigator.userActivation.isActive`, which proves the ask came from the gesture) has granted, in an init script; the prompt then goes to `ready`. Playwright's `setInputFiles` accepts a directory path for the first and a `.zip` for the second; wait until `__DDI_DEBUG.songs.importing` is false (then `songs.imported`, `songs.packs` and `songs.report` say what came in). Imports land in IndexedDB (`ddi-library`, stores `songs` and `files`), so use a fresh browser context for a clean library. Build test packs in a scratch dir (a pack folder of song folders; copy a bundled song, rename files to test case-insensitive lookups, write a short `.sm` by hand to cover rolls, mines, lifts and fakes, and zip it with `zip -r` and `zip -r0` for deflated and stored entries). An autoplayed chart must end with only top-tier judgements, `let_go` 0 and no mines hit. FFR levels import the same way (a folder of level SWFs, or an `.as`/`.beatbox` text beside its audio; a level a song, its folder its pack, id `u-` + FNV-1a 64 of `pack/file name` lowercased): write first-party ones with `DDI_FFR_FIXTURES=<dir> cargo test -p ddi-desktop --test ffr_levels -- --ignored` (never use real FFR levels in the repository).

## Headless Firefox

Launch through `firefox.mjs` (next to this file), never with a bare `firefox.launch`:

```js
import { firefox } from 'playwright-core';
import { launchFirefox } from '<repo>/.claude/skills/verify/firefox.mjs';
const browser = await launchFirefox(firefox);                  // Playwright's Firefox build
const browser = await launchFirefox(firefox, { stock: true }); // /Applications/Firefox.app over WebDriver BiDi (DDI_FIREFOX_STOCK=1, the maintainer only)
```

Playwright's build needs `npx playwright-core install firefox` once (per playwright-core version); `stock: true` runs the Firefox the maintainer uses, and only with `DDI_FIREFOX_STOCK=1`, which agents never set: Playwright then runs `xattr` over the app bundle and macOS shows the maintainer a system-access prompt. The helper also turns the Gamepad API off (polling controllers asks macOS for Input Monitoring); the game's fake pad (`window.__DDI_FAKE_PAD`) works without it, and `prefs: { 'dom.gamepad.enabled': true }` turns it back on. On macOS a bare launch quits with "Could not find profile folder.": `~/Library/Application Support/Firefox` opens only to Firefox itself, and a Firefox started from a terminal runs on the terminal's behalf. The helper points `MOZ_APP_DATA`/`MOZ_LOCAL_APP_DATA` at a temporary folder (removed on close), so Firefox never reads or writes the maintainer's profiles. It also allows autoplay and mutes the output (`media.volume_scale` 0; the output peak in `__DDI_DEBUG.audio` still reads the real level); pass `sound: true` to hear it, `prefs` for more preferences.

Headless Firefox gets no WebGPU adapter (Playwright's build logs "WebGPU is disabled by blocklist"), so play runs on WebGL2; Firefox's WebGPU path stays a manual check. Autoplay to the results (all top tier), `&auto=pad` with `fake-gamepad.js`, and folder import with `setInputFiles` work as in Chrome. Firefox has no `showDirectoryPicker`, so input 0 is the folder input without deleting anything. Recipes that use CDP (touch events, network throttling) are Chrome-only.

Performance numbers for Firefox come from the stock Firefox (`launchFirefox(firefox, { stock: true })`, a maintainer's run; an agent reports Playwright's numbers as such): Playwright's Nightly build runs our wasm several times slower (rAF callbacks 6–12 ms where the stock Firefox takes 2 ms, with frames dropped), so it says nothing about what the maintainer feels. On an unattended Mac with the display asleep (`system_profiler SPDisplaysDataType` says "Display Asleep: Yes"), every browser's frame clock but WebKit's stalls about 0.5–0.7 s every ~11.7 s, on about:blank too (Chrome's trace shows the GPU process waiting in `SwapBuffers`): frame-time checks ignore that rhythm or run with the display awake.

## Headless WebKit

Playwright cannot drive Safari; it drives its own WebKit build (`npx playwright-core install webkit` once), close to Safari's engine but not Safari's app or media policies. `webkit.launch({ headless: true })` needs no setup: `127.0.0.1` is a secure context, WebGPU works headless, Ogg Opus decodes natively (so the Opus fallback runs there only when forced), and autoplay, `&auto=pad` with `fake-gamepad.js` and folder `setInputFiles` work as in Chrome. It has no mute switch: add `mute-audio.js` (next to this file) with `context.addInitScript({ path })`, which routes the destination through a zero gain after the game's meter.

It plays audio without any user gesture, even in a fresh context, so it cannot catch Safari's gesture rule; that stays a manual Safari check. Its `newContext()` sessions are ephemeral like a private window, where IndexedDB refuses to store Blobs and Files; test imports in `webkit.launchPersistentContext(<fresh temp dir>, { headless: true })` instead (one fresh dir per clean library).

## Gamepads without hardware

`fake-gamepad.js` (next to this file) replaces `navigator.getGamepads` with scripted pads: `page.addInitScript({ path })`, then `window.__DDI_FAKE_PAD.add({ id, mapping: '' | 'standard', buttons, axes, hatAxis, trustTimestamp })`, `.press(i, control)`, `.release(i, control)`, `.disconnect(i)`, with controls as stored in bindings (`button:3`, `axis:1-`, `hat:9:left`). Add the pad in an init script (before the app loads) or later; the app finds pads by polling. Bindings for a non-standard pad can be seeded in `localStorage` (`ddi.settings.v1`, `pads: [{ id, single: [[…], …], layouts: { "dance-solo": [[…], …] }, start, back }]`; keyboard tables per layout under `keys`); a standard pad gets the d-pad/face-button defaults for each built-in layout. Two fake pads with the same id play one half of `dance-double` each (lower index on the left) with their single bindings; `__DDI_DEBUG.pressed` shows which of the eight lanes are down.

`#/play?…&auto=pad` autoplays through pad 0: the autoplayer schedules each press on the fake pad ahead of time (`schedule(hostMs, control, pressed)`), the fake applies it when `getGamepads()` is called at or after that time, and the edge reaches the engine through the real poller. With `trustTimestamp: true` the pad's `timestamp` is the exact edge time and the mean error should be ~0 ms; with `false` the app stamps the poll time and the mean should be about +0.5 ms (1 ms loop), σ well under 1 ms. `__DDI_DEBUG.pads` shows how each pad's edges were stamped, `pad_polls` the polls per second (~900 with the 1 ms loop) and `pad_fast` whether the loop runs. A fresh profile shows the prompt's new-device step; Start (button 9 on a standard pad) continues past it. Gamepad presses count as a user gesture in Chrome and Firefox only for real pads, so the headless autoplay flag is what lets the audio start here.

**Every desktop run that is not the maintainer's own sets `DDI_HOME`** to a scratch folder (`DDI_HOME=$PWD/target/scratch/<you>/home cargo run -- …`; the run's settings, history, library cache and compiled video decoder go to its `config/`, `data/` and `cache/`): without it a run writes the maintainer's real `storage.json` (an options run with a fake pad once turned Reverse on there). A window draws no frames while the display sleeps, and a covered window interrupts a play (as a hidden page does): pictures come from the offscreen tests (`crates/desktop/tests/play_offscreen.rs`, `play_flow.rs`, `play_movie.rs`).

On desktop (no browser), `cargo run -- --screen options --seconds 4 --fake-pad "1.0:13+,1.1:13-,2.0:0+,2.1:0-"` plays a scripted standard pad (W3C button numbers, seconds from the start) through the same thread, tracker and menu routing as gilrs's pads; the run's last lines say how many keys took the OS's time and how many pad edges went to menus or to a bind dialog. ## Replays

A kept play is watched again on the play route (`docs/plans/play-history.md`, "Replays"): `#/play?replay=<play id>` (the id is `__DDI_DEBUG.history.last.id` after a play) shows the start prompt marked REPLAY (Enter starts; no new-device step), plays the chart with the record's options, rules, song offset and drawing settings, its log on the lanes (live keys, pads and taps reach none; Escape twice or held still quits, to `#/`), and ends on the results marked REPLAY (`__DDI_DEBUG.results.line` ends `· REPLAY`, the first note says when it was played; `Retry` reads "Watch again"; no offset editor). `&view=results` opens the kept play's results at once (judged again from its log; `WatchReplay` and `SongList` only). `window.__DDI_DEBUG.replay` (kept across frames): `{id, state: loading|ready|refused|playing|results|ended, refused, fed, edges, check: {matches, withRecord, problems}}`; `check.matches` must be true and its results equal the play's (`grade`, `score`, `tiers`, `stats`, `hits`, `lifePoints`), and `history.count` must not grow. A play's own results offer "Watch replay" (`ui.rects.WatchReplay`, key `W`, once it is kept). On song select, `P` (or the footer's `Link.Plays`) opens the chosen chart's plays: `ui.theme.plays` (`id|when|grade score lamp|mods` a row), `ui.theme.playsSelected`, rows at `ui.rects.Row<i>` (a tap chooses one), buttons `Watch` (focused: Enter watches the chosen, the best at first), `Open` (its results), `Remove` (twice), `Newer`/`Older`, `Close`; `W` on song select watches the chosen chart's best. Refusals show on the prompt (`prompt.step` `error`, `prompt.error` "This replay cannot be watched. …"): a play id not kept, a chart whose notes changed, a song gone, a skin not installed. `__DDI_LOSE_DEVICE()` mid-replay brings the prompt back; Enter replays from the start. Desktop: `--replay ID [--results] [--start]`; tests `crates/desktop/tests/replay.rs` (no device) and `replay_flow.rs` (offscreen).

The ghost (`"ghost": true` in `ddi.settings.v1`, Options → Display → "Ghost of your best", off by default) needs a best: autoplays never count, so for a test keep an autoplay as the player's own (copy its `plays` and `play_summaries` values under a new id with `record.autoplay` null and `autoplay` false, then reload the page: the history reads the summaries at start). Edit a record as text (a regular expression on its `"autoplay":{…}`), never through `JSON.parse`/`JSON.stringify`: JavaScript numbers lose the 64-bit shuffle seed's low bits, and a Shuffle play would then replay another order. A play of that chart then shows its lead under the score, and `__DDI_DEBUG.ghost` says it (percentage points, or points; negative behind); at the end it is the difference of the two results' scores.
